# terminal-pane Specification

## Purpose

The terminal is a de-singletonized, self-contained pane instance (own xterm + data socket + report gating + touch/selection state), with the Ctrl+Shift+C/V combo handled once and the desktop-shared input surfaces routed to the focused pane.

## Requirements

### Requirement: The terminal is a self-contained instance component

Each on-screen terminal SHALL be a `TerminalPane` that owns its own xterm instance, its own
per-session `WsClient`, and its own replay-suppression state (the `snapshot` marker → discard
terminal-generated input during replay, guarded against superseded sockets). Two instances SHALL
share no socket, suppression flag, or fit loop. In the single-slot case (one `TerminalPane`),
observable behavior — replay on reconnect, resize, exit overlay, clipboard, upload injection — SHALL
be identical to the pre-refactor app.

#### Scenario: Single terminal unchanged after refactor

- **WHEN** the app runs with no split (one terminal tab)
- **THEN** reconnect replay, PTY resize, Ctrl+Shift+C/V, drag-drop upload, and the exit overlay
  behave exactly as before the refactor

#### Scenario: Two terminals are independent

- **WHEN** two terminal tabs are shown in a split
- **THEN** each has its own live socket and screen; output, scrollback, and resize in one do not
  affect the other

### Requirement: Terminal reports keep today's per-document gating, carried per pane

Each `TerminalPane` SHALL gate terminal-generated reports (answers to DA/DSR/size/mode queries)
exactly as the app does today — forwarded only when `document.hasFocus()`, with the existing grace
window after focus is (re)gained — as component-local state. Slot focus SHALL play NO part in
report-gating: two split slots are two different PTYs (a tab id occupies at most one slot), so
in-window duplication cannot occur, and an unfocused slot MUST still answer its own PTY's queries
or background programs (vim, tmux, width probes) would hang.

#### Scenario: The unfocused slot answers its own PTY's query

- **WHEN** a program in the UNFOCUSED split terminal emits a Device Attributes query and the
  document has focus
- **THEN** that pane forwards the response to its own PTY and the program proceeds normally

#### Scenario: Replay suppression is preserved per pane

- **WHEN** a pane reconnects and the server replays its snapshot
- **THEN** no terminal-generated bytes from parsing the replay reach that pane's PTY

#### Scenario: Unfocused terminal still shows output

- **WHEN** a background command prints to the unfocused split terminal
- **THEN** its screen updates normally

### Requirement: The Ctrl+Shift+C/V combo is handled once, routed to the focused pane

The clipboard combo SHALL be handled by a single app-level capture listener that dispatches to the
focused `TerminalPane` (today `useTerminal` installs one window-level listener PER instance — two
panes would paste into both shells). Each pane keeps its xterm-level opt-out so the combo never
reaches a shell.

#### Scenario: Paste goes to exactly one shell

- **WHEN** two split terminals are shown and the user presses Ctrl+Shift+V
- **THEN** the clipboard text is pasted into only the focused terminal

#### Scenario: Copy takes the focused pane's selection

- **WHEN** both split terminals hold selections and the user presses Ctrl+Shift+C
- **THEN** the focused pane's selection lands in the clipboard

### Requirement: Touch/selection state is instance-scoped

Per-terminal touch state SHALL be scoped to the pane instance — gesture state, selection endpoints
(today a module-level `lastSelection` in `terminal/touch.ts`), and selection handles. Gestures and
selection handles SHALL bind per pane (events arrive on a specific pane's host with pane-local
coordinates); a tap on a pane additionally focuses its slot.

#### Scenario: Selections in both terminals stay independent

- **WHEN** the user long-press-selects in split terminal A, then makes a selection in terminal B,
  then drags one of A's selection handles
- **THEN** the drag adjusts only A's selection using A's buffer coordinates

### Requirement: The focused pane receives the desktop-shared input surfaces

The desktop-shared input surfaces SHALL target the currently focused `TerminalPane` — the
Ctrl+Shift+C/V clipboard combo and the upload picker / clipboard-paste actions. Clicking a slot (or
last-interacted) SHALL redirect these to it. (Split is desktop-only, so the soft keyboard, extra-
keys bar, and touch gestures — mobile-only surfaces — never coexist with a split and keep their
single-slot behavior unchanged.)

#### Scenario: Upload targets the focused terminal

- **WHEN** the user clicks slot B to focus it and then uses the topbar upload picker
- **THEN** the file path is injected into slot B's shell

#### Scenario: Single-slot mobile input is unchanged

- **WHEN** the mobile layer is active (never split)
- **THEN** the soft keyboard and extra-keys bar target the sole terminal exactly as before this
  change
